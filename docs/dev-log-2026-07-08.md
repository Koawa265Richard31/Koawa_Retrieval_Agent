## Learning: Streaming RAG Main Chain

Read the first-day RAG chat entry chain:

```text
Client
  -> RAGChatController
  -> RAGChatServiceImpl
  -> StreamCallbackFactory
  -> ChatQueueLimiter
  -> StreamChatTraceRunner
  -> StreamChatPipeline
  -> LLMService.streamChat
  -> StreamChatEventHandler
  -> SSE response + assistant message persistence
```

Key understanding:

- `RAGChatController` is a thin HTTP/SSE entry.
- `RAGChatServiceImpl` prepares one chat task: `conversationId`, `taskId`, callback, queue, trace, and pipeline context.
- `StreamChatContext` carries fixed task inputs and pipeline-produced intermediate state.
- `StreamChatPipeline` is a fixed RAG pipeline, not an agent loop.
- `StreamChatEventHandler` sends streaming chunks to the frontend and persists the final assistant reply.
- `StreamChatTraceRunner` wraps the callback and records trace lifecycle, including first output and completion/failure.

Agentic RAG conclusion:

```text
Current system = static RAG pipeline.
Future agent mode should branch near RAGChatServiceImpl and reuse existing retrieval, MCP, memory, trace, and SSE capabilities.
```

## Learning: StreamChatPipeline

Read the main `StreamChatPipeline.execute(ctx)` flow:

```text
loadMemory
  -> rewriteQuery
  -> resolveIntents
  -> handleGuidance
  -> handleSystemOnly
  -> retrieve
  -> handleEmptyRetrieval
  -> streamRagResponse
```

Important conclusions:

- `loadMemory` loads conversation history and appends the current user question.
- `rewriteQuery` rewrites and splits the current question.
- `resolveIntents` maps sub-questions to intent nodes.
- `handleGuidance` and `handleSystemOnly` are short-circuit branches.
- `retrieve` is where KB/MCP context is prepared.
- `streamRagResponse` builds prompt messages and starts the streaming LLM call.

## Learning: Retrieval Pipeline

Started reading `RetrievalEngine.retrieve(subIntents, topK)`.

Main flow:

```text
RetrievalEngine.retrieve
  -> for each SubQuestionIntent
    -> buildSubQuestionContext
      -> split node scores into kbIntents and mcpIntents
      -> retrieveAndRerank for KB
      -> executeMcpAndMerge for MCP
    -> return SubQuestionContext
  -> merge all SubQuestionContext values
  -> return RetrievalContext
```

Key understanding:

- `RetrievalContext` is the final carrier used by prompt building.
- It contains `kbContext`, `mcpContext`, and `intentChunks`.
- KB and MCP are both handled inside `buildSubQuestionContext`.
- KB retrieval goes through `retrieveAndRerank`.
- MCP tool execution goes through `executeMcpAndMerge`.

Important correction:

```text
Sub-question intent and KB chunks are not strictly one-to-one.
```

In `retrieveAndRerank`, the retrieved chunks for the current sub-question are assigned to each matched KB intent:

```text
intent A -> same retrieved chunks
intent B -> same retrieved chunks
```

This is a coarse association because `multiChannelRetrievalEngine.retrieveKnowledgeChannels(...)` returns chunks that are not precisely attributed back to a single intent node.

## Learning: KB Context Formatting

Read `contextFormatter.formatKbContext(kbIntents, intentChunks, topK)`.

Purpose:

```text
Convert intent rules + retrieved chunks into prompt-ready KB context text.
```

It does not retrieve, rerank, or call the model. It only formats text.

Cases:

```text
No chunks:
  return empty string

No KB intents:
  format chunks directly

Single KB intent:
  promptSnippet for that intent + its chunks

Multiple KB intents:
  merge promptSnippets + merge/de-duplicate chunks
```

Mental model:

```text
formatKbContext = build the "knowledge context block" that will later be inserted into the LLM prompt.
```

## Startup Probe

Attempted to start the current backend without LLM API keys.

Result:

```text
LLM API keys are not the current startup blocker.
```

Observed startup dependency order:

```text
Maven module install required first
Redis required
RocketMQ required
PostgreSQL likely required for real endpoint usage
MCP server can fail gracefully during registration
```

Actions and findings:

- `mvnw -q -DskipTests install` succeeded.
- Direct `spring-boot:run` for `bootstrap` entered Spring Boot successfully.
- Redis initially failed because local Redis had no password while project expects `123456`.
- Temporarily set local Redis password with `redis-cli CONFIG SET requirepass 123456`.
- After Redis passed, startup reached Tomcat and MyBatis initialization.
- Final blocker was RocketMQ NameServer/Broker not running on `127.0.0.1:9876`.
- Docker CLI exists, but Docker daemon/Desktop was not available in the current environment.
- No local `mqnamesrv` / `mqbroker` command was found.

Current startup status:

```text
Backend cannot fully start in the current environment until RocketMQ is available
or a local no-MQ development profile is added.
```
